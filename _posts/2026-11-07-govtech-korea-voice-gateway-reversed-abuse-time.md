시나리오 통합 테스트에서 상담원 화면의 폭언 기록이 `00:00:39 ~ 00:00:38`처럼 **끝이 시작보다 빠르게** 찍혔다. 카운트와 차단은 맞았지만 기록이 이상하면 상담 기록으로 쓸 수 없다. 원인은 STT 서버가 보내는 발화 시작 알림의 번호였다. ([PR #96](https://github.com/GovTech-korea/GovTech-Korea_VoiceGateway/pull/96))

## 변경 내용

| 위치 | 변경 |
|---|---|
| `StreamingAsrStream` | 이미 시작한 발화 번호로 `speech_start`가 다시 오면 다음 발화의 시작으로 기록 |
| `StreamingAsrStream` | STT 오류(`error`)를 받으면 기록해 둔 발화 시작을 비움 |
| `CallCoordinator` | 시작을 모르면 기록 시작을 끝 이하로 맞추고, 폭언 겹침 판정은 끝 시각 기준 |

## 진행 과정

### 재현

증상은 쉬지 않고 욕을 이어 한 실통화 녹음(시나리오 ⑤, ⑦)에서만 나왔다. 로컬 게이트웨이에 같은 녹음을 흘리고 상담원이 받는 메시지를 연결 기준 시각으로 찍었다.

```
38.37 {"kind": "ABUSE", "startMs": 38368, "endMs": 37711, "text": "고 지금 야 씨발 씨발 미친 새끼", ...}
```

`startMs`가 메시지를 받은 시각(38.37초)과 같다. 게이트웨이는 발화 시작을 모르면(`null`) **지금 시각**을 시작으로 쓴다. 끝은 STT에 마지막으로 넘긴 음성의 시각이라 지금보다 0.6초쯤 앞선다. 그래서 시작이 끝보다 늦어졌다.

### 왜 시작을 몰랐나

STT 서버는 음성이 시작되면 `speech_start`를, 문장이 끝나면 `final`을 보낸다. 게이트웨이는 `speech_start`의 발화 번호로 시작 시각을 기억해 두고, 같은 번호의 `final`에서 지운다.

팀원 STT 서버 코드를 읽어 보니 순서가 이렇다.

1. 음성 감지(VAD)가 말이 시작된 것을 보면 그 자리에서 `speech_start`를 보낸다.
2. `final`은 모아 둔 음성을 디코딩한 **뒤에** 보내고, 그다음에 발화 번호를 1 올린다.

쉬지 않고 이어 말하면 앞 문장의 디코딩이 끝나기 전에 다음 말이 시작된다. 그러면 다음 발화의 `speech_start`가 **아직 올리지 않은 앞 발화 번호**로 나간다.

| STT가 보낸 것 | 게이트웨이가 한 일 (수정 전) |
|---|---|
| `speech_start` id 4 (앞 문장) | 4번 시작 기록 |
| `speech_start` id 4 (다음 문장) | 4번 시작을 덮어씀 |
| `final` id 4 | 4번 시작 삭제 |
| `partial` id 5 | 5번 시작 없음 → 지금 시각 |

### 수정

같은 번호의 `speech_start`가 다시 오는 경우는 다음 발화가 시작된 경우뿐이다. VAD가 다시 "시작"을 알리려면 그사이에 문장 끝(endpoint)이 있어야 하기 때문이다. 그래서 비어 있는 다음 번호에 기록한다.

```java
case "speech_start" -> {
	long frame = Math.round(message.path("audio_start").asDouble(0) * 1000 / FRAME_MS);
	int id = message.path("id").asInt();
	// 앞 발화의 final이 나오기 전에 다음 발화가 시작되면 서버가 앞 발화 id로 보낸다: 이미 시작한 발화면 다음 발화의 시작이다
	while (utteranceStartFrame.containsKey(id)) {
		id++;
	}
	utteranceStartFrame.put(id, frame);
}
```

코드 리뷰에서 빠진 경우가 하나 나왔다. STT 디코딩이 실패하면 서버는 `final`도 `discard`도 보내지 않고 번호도 올리지 않는다. 그러면 남은 시작 기록 때문에 이후 발화가 통화 끝까지 한 칸씩 밀린다. 그래서 `error`를 받으면 기록을 비운다. 그때 진행 중이던 발화는 시작을 모르게 되지만, 기록 시작을 끝 이하로 맞추는 처리가 있어서 거꾸로 나오지 않는다.

수정 후 같은 녹음 두 개를 다시 흘렸다. 폭언 기록 9건이 모두 시작 ≤ 끝으로 나왔다.

## 새로 배운 것

- **스트리밍 STT의 이벤트 번호는 "보내는 시점의 번호"다.** 감지(VAD)는 음성이 들어오자마자, 인식 결과는 디코딩이 끝난 뒤 나간다. 두 이벤트가 같은 번호 체계를 쓰면 빠르게 이어 말할 때 번호가 어긋날 수 있다. 받는 쪽에서 "이 번호는 이미 시작했다"는 사실로 다음 발화를 알아낼 수 있다.
- **시각을 모를 때 '지금'으로 채우면 다른 시계와 섞인다.** 기록의 끝은 음성을 받은 시각이고, 대신 넣은 시작은 처리한 시각이다. 둘은 STT 지연만큼 어긋난다.
