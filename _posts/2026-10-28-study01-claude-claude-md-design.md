## 목적

프로젝트를 시작하면서, 코드보다 먼저 **Claude가 따를 규칙**부터 정리했다.

이번에 원한 것은 두 가지다.

- Claude가 상황마다 **필요한 규칙만** 찾아 읽을 것
- 보안, 작업 기록, 코드 작성 절차처럼 **항상 지켜야 하는 규칙**은 절대 빠지지 않을 것

## 접근 방식

CLAUDE.md는 **길잡이**로만 쓰고, 실제 규칙은 주제별 문서로 나눈다.

```
<작업 폴더>/
├─ CLAUDE.md              ← 길잡이: "이럴 때는 이 문서를 보라"만 있다
├─ .claude/
│   ├─ docs/              ← 주제별 규칙 문서
│   ├─ worklog.md         ← 작업 기록
│   └─ blog-drafts/       ← 블로그 초안
└─ <git 저장소>/          ← 실제 코드
```

## 처음 구상

처음에는 길잡이 표 하나에 문서를 나열했다.

| 이럴 때 | 이 문서를 볼 것 |
|---|---|
| 커밋, 브랜치, push, merge 할 때 | `.claude/docs/git-workflow.md` |
| ... | ... |

문서 내용을 길잡이에 `@경로`로 불러오는 방법도 있지만 쓰지 않았다. `@`로 연결한 문서는 대화를 시작할 때마다 **통째로 불러와진다.** 그러면 나눠 둔 의미가 없다. 그래서 경로만 적어 두고, 필요할 때 Claude가 직접 읽게 했다.

## 구현

규칙을 이야기하다 보니 문서가 여덟 개가 됐다. 그리고 성격이 두 가지로 갈렸다.

**항상 적용되는 규칙**

| 문서 | 내용 |
|---|---|
| `security.md` | 밖에 공개하면 안 되는 정보를 정의하고, 저장소와 외부 글에서 각각 어떻게 다루는지 |
| `tracking.md` | 결정, 변경, 테스트, 문제를 시각과 이유까지 기록하는 규칙 |
| `coding-process.md` | 한 번에 최대 클래스 하나, 메소드는 하나씩 컨펌받고 진행 |

**상황에 따라 보는 규칙**

| 문서 | 언제 |
|---|---|
| `tech-spec.md` | 어떤 기술과 버전을 쓰는지 알아야 할 때, 의존성을 바꿀 때 |
| `profiles.md` | 설정 파일, 실행 프로필(local, dev, production)을 다룰 때 |
| `git-workflow.md` | 브랜치를 만들거나 merge, push 할 때 |
| `commit-convention.md` | 커밋 메시지를 쓸 때 |
| `blog.md` | 기능이 `production` 브랜치에 들어간 뒤, 블로그 글을 쓸 때 |

## 다시 구상

표 하나에 다 섞어 두니 문제가 보였다. "커밋할 때"처럼 상황이 분명한 규칙은 잘 찾지만, 보안이나 작업 기록처럼 **모든 작업에 걸리는 규칙**은 "이럴 때"라는 조건이 애매했다. 그러면 놓치기 쉽다.

그래서 길잡이를 두 칸으로 나눴다.

```markdown
## 항상
| 이럴 때 | 이 문서를 볼 것 |
| 모든 작업 (보안이 최우선) | .claude/docs/security.md |
| 무언가를 정하거나 바꾸거나 실행했을 때 | .claude/docs/tracking.md |
| 코드를 작성하거나 수정할 때 | .claude/docs/coding-process.md |

## 상황별
| 이럴 때 | 이 문서를 볼 것 |
| 브랜치를 만들거나 merge, push 할 때 | .claude/docs/git-workflow.md |
| ... | ... |
```

길잡이 자체는 20줄이 안 된다. 상세 내용은 전부 문서 쪽에 있다.

### 작업 기록을 따로 둔 이유

나중에 "내가 언제 이렇게 정했고, 언제 왜 바꿨지?"를 물어보고 싶었다. 대화는 끝나면 사라지고, git 기록에는 결정한 이유가 남지 않는다. 그래서 `worklog.md`에 시간 순으로 남기게 했다.

```
- 13:20 [변경] 블로그 제목 형식
  - 바뀐 것: <이전> → <이후>
  - 이유: <내가 말한 이유 그대로>
```

분류는 `결정`, `변경`, `설계`, `구현`, `테스트`, `문제`, `보류` 등으로 나눴다. 특히 `변경`에는 반드시 "이전 → 이후"를 적게 했다. 블로그 글도 이 기록을 재료로 쓴다.

### 코드는 메소드 하나씩

한 번에 많이 만들어 놓고 나중에 고치는 방식은 피하고 싶었다. 코드 한 줄 한 줄을 이해하면서 가는 게 공부의 목적이기도 하다. 그래서 `coding-process.md`에 순서를 못박았다.

1. 클래스 이름, 역할, 메소드 목록을 먼저 보여주고 컨펌
2. 메소드 하나를 보여주고 컨펌받은 뒤에만 파일에 반영
3. 컨펌 전에는 다음 메소드로 넘어가지 않음

## 겪은 문제

**1. 기록이 엉뚱한 곳에 붙었다.** 작업 기록 파일 맨 아래에 "보류 목록"을 두었더니, 새 기록이 보류 목록 밑에 붙어 버렸다. "새 기록은 보류 목록 위에 넣는다"는 한 줄을 규칙에 추가해서 해결했다. 사람에게는 당연한 배치도 문서에 적어야 한다.

**2. 규칙이 자주 바뀐다.** 블로그 제목 형식만 하루에 세 번 바뀌었다. 규칙을 문서 하나에 몰아 두지 않고 주제별로 나눠 두었기 때문에, 바뀔 때마다 해당 문서 하나만 고치면 됐다. 바뀐 이력은 작업 기록에 남는다.

## 새로 배운 것

- CLAUDE.md의 `@경로` 불러오기는 편하지만 매번 전부 읽힌다. "필요할 때 읽어라"로 쓰려면 경로만 적는다.
- 길잡이는 **"언제 볼지"를 구체적으로** 쓰는 게 핵심이다. "Git 관련"보다 "브랜치를 만들거나 merge, push 할 때"가 훨씬 잘 지켜진다.
- 모든 작업에 걸리는 규칙은 "항상" 칸으로 따로 빼야 빠지지 않는다.
