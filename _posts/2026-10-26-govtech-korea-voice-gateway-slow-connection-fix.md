[상담 연결 구현]({% post_url 2026-10-26-govtech-korea-voice-gateway-call-routing %}) PR 전에 돌린 리뷰에서 전송 계층 문제가 나와, 바로 고쳤다 ([PR #17](https://github.com/GovTech-korea/GovTech-Korea_VoiceGateway/pull/17)).

## 문제 1: 처리되지 않는 예외 하나가 엉뚱한 사람을 끊는다

WebSocket 세션을 여러 스레드가 동시에 쓰려고 Spring의 `ConcurrentWebSocketSessionDecorator`로 감싸 두었다. 이 데코레이터는 전송이 2초를 넘거나 버퍼가 한도를 넘으면 `SessionLimitExceededException`을 던진다. 그런데 이 예외는 `RuntimeException`이라 `IOException`만 잡던 코드를 그대로 빠져나갔다.

상담원 네트워크가 멈췄을 때 실제로 일어나는 일은 이렇다.

1. 민원인 음성을 상담원에게 보내던 **민원인 쪽 스레드**에서 예외가 난다
2. 예외가 민원인 메시지 처리부를 빠져나가, Spring이 **민원인 연결**을 닫는다. 민원인은 통화 종료 메시지도 받지 못한다
3. 정작 문제인 상담원 연결은 열린 채로 남는다. 데코레이터가 그 뒤 모든 전송을 조용히 버린다
4. 상담원은 여전히 "대기 중"으로 남아 다음 민원인이 계속 배정된다

## 문제 2: 잠금을 쥔 채 네트워크로 보낸다

상담 상태(큐, 배정, 벨)는 잠금 하나로 지킨다. 그런데 메시지 전송도 그 잠금 안에서 하고 있었다. 송신 버퍼가 꽉 찬 상담원에게 보내는 동안 잠금이 잡혀 있으면, 그 시간만큼 **다른 모든 상담원·민원인의 처리가 멈춘다.**

## 해결: 연결마다 전송 전용 가상 스레드

두 문제를 한 번에 풀었다. 연결마다 **전송 전용 스레드 하나와 대기열**을 둔다.

```java
this.sender = Executors.newSingleThreadExecutor(
        Thread.ofVirtual().name("ws-send-" + session.getId()).factory());

private void enqueue(WebSocketMessage<?> message) {
    if (pending.incrementAndGet() > MAX_PENDING) {   // 약 5초 분량이 쌓이면
        abort("전송 대기열 초과");                      // 받지 못하는 연결로 보고 닫는다
        return;
    }
    sender.execute(() -> {
        try {
            session.sendMessage(message);
        } catch (Exception e) {
            abort("전송 실패: " + e.getMessage());     // 실패하면 그 연결만 닫는다
        } finally {
            pending.decrementAndGet();
        }
    });
}
```

- **보내기는 대기열에 넣고 바로 돌아온다.** 상태 잠금 안에서 불러도 느린 상대 때문에 막히지 않는다.
- **연결당 스레드 하나라 순서가 지켜진다.** "벨 울림" 다음에 "벨 취소"가 가야지, 거꾸로 가면 앱이 꼬인다.
- **실패한 연결은 그 연결만 닫는다.** 닫으면 Spring이 "연결 끊김"을 알려 주고, 기존 정리 로직(통화 종료, 대기 목록에서 제거)이 그대로 돈다.

Java 21부터 쓸 수 있는 **가상 스레드**라서 연결마다 스레드를 하나씩 둬도 부담이 작다. 가상 스레드는 OS 스레드가 아니라 JVM이 관리하는 가벼운 스레드라, 수천 개를 만들어도 된다.

### 왜 "잠금 밖에서 보내기"가 아니었나

처음 떠올린 방법은 잠금 안에서 보낼 메시지만 모아 두고, 잠금을 푼 뒤 보내는 것이었다. 하지만 이러면 **서로 다른 스레드의 전송 순서가 뒤집힐 수 있다.** 벨 타이머 스레드의 "벨 취소"가 배정 스레드의 "벨 울림"보다 먼저 나갈 수 있다. 잠금 안에서 "대기열에 넣기"만 하면 상태가 바뀐 순서 그대로 대기열에 들어가고, 그 순서대로 나간다.

## 덤으로 고친 것 2개

| 문제 | 원인 | 수정 |
|---|---|---|
| 재접속 직후 이전 벨 타이머가 새 벨을 끊음 | 타이머가 상담원을 `agentId` 문자열로 확인 | 벨을 울린 **상담원 객체 자체**와 비교 |
| READY를 다시 보내면 대기 순번을 잃음 | READY 요청마다 순번을 새로 받음 | 이미 READY면 순번 유지 |

첫 번째는 "타이머 콜백이 실행을 시작해 잠금을 기다리는 사이 재접속"이라는 아주 좁은 타이밍이다. 테스트용 타이머에 "취소됐어도 이미 시작된 콜백을 실행"하는 기능을 넣어 재현했다. 그리고 **수정 전 코드로 돌리면 이 테스트가 실패하는 것**까지 확인했다. 그래야 테스트가 진짜 버그를 잡고 있다고 믿을 수 있다.

## 테스트

전체 47개 통과. 전송 대기열은 Mockito로 만든 가짜 세션으로 확인했다.

- 넣은 순서대로 보내고, 닫기는 앞의 메시지를 다 보낸 뒤
- 상대가 느려도 보내는 쪽은 바로 돌아옴
- 전송 실패 / 대기열 초과 → `SESSION_NOT_RELIABLE`로 닫힘
