## Q1. 브라우저 주소창에 URL을 입력하고 엔터를 치면, 화면이 뜰 때까지 어떤 일이 일어나는가? (시작 질문)

### 내 답변

(처음) DNS와 연결된 IP로 이동한다.

(배운 뒤) DNS 조회로 IP 주소를 알아내고, TCP 연결을 시도해서 3-way handshake를 한다. 그리고 TLS handshake도 한다. 여기서 비대칭키로 대칭키가 오고간다. HTTP로 요청하면 서버에서 HTML을 보내고, 클라이언트가 200을 보내면 렌더링을 시작한다. 연결을 끊을 때는 4-way handshake로 종료한다.

### 모범 답변

`https://www.example.com`을 입력했다고 하자.

| 순서 | 단계 | 하는 일 |
|---|---|---|
| 1 | **DNS 조회** | `www.example.com` → IP 주소 |
| 2 | **TCP 연결** | 그 IP의 443번 포트로 3-way handshake |
| 3 | **TLS handshake** | 서버 인증서를 CA로 검증하고, 세션 키(대칭키)를 정한다 |
| 4 | **HTTP 요청** | `GET / HTTP/1.1` 등을 암호화해서 보낸다 |
| 5 | **서버 처리** | 요청을 처리해 HTML을 만든다 |
| 6 | **HTTP 응답** | `200 OK`(상태 코드) + HTML이 **서버에서** 돌아온다 |
| 7 | **렌더링** | 브라우저가 HTML을 읽고, CSS·JS·이미지를 발견하면 **추가로 요청**하며 화면을 그린다 |
| 8 | **연결 종료/재사용** | 4-way handshake로 끊거나, Keep-Alive로 다음 요청에 재사용한다 |

DNS는 한 번에 찾지 않고 가까운 곳부터 묻는다.

```
브라우저 캐시 → OS 캐시 → hosts 파일 → DNS 서버
                                         ↓
                      루트 서버 → .com 서버 → example.com의 서버
```

면접용 한 줄:
> "DNS로 IP를 얻고, TCP 3-way로 연결하고, HTTPS면 TLS handshake로 인증서를 확인하고 세션 키를 정합니다. 그다음 HTTP 요청을 보내면 서버가 상태 코드와 HTML을 응답하고, 브라우저는 추가 리소스를 요청하며 렌더링합니다. 연결은 Keep-Alive로 재사용하거나 4-way로 종료합니다."

### ✅ 맞게 알고 있던 부분

- **전체 순서**를 정확하게 이었다. DNS → TCP 3-way → TLS → HTTP → 렌더링 → 4-way 종료까지, 앞의 세 글에서 배운 것을 한 줄로 연결했다.
- TLS에서 **비대칭키로 대칭키를 정한다**는 핵심을 기억했다.

### ❌ 잘못 알고 있던 부분

- **처음 답은 DNS에서 멈췄다.** IP를 알아낸 건 시작일 뿐이고, 그 뒤에 연결·요청·응답·렌더링이 있다. 그리고 IP로 "이동"하는 것이 아니라 서버에 **요청을 보내는** 것이다.
- **"클라이언트가 200을 보낸다"는 방향이 반대다.** `200 OK`는 **서버**가 응답에 붙여 보내는 상태 코드다.
- **빠진 단계:** 렌더링 중의 **추가 리소스 요청**(CSS·JS·이미지), TLS 단계의 **인증서 검증**, 종료 대신 **Keep-Alive 재사용**.

## Q2. DNS는 TCP와 UDP 중 무엇을 쓰는가? (꼬리질문)

### 내 답변

(처음) TCP를 쓸 것 같다. 표시해야 할 것들을 정확하게 전부 보장해야 하니까.

(배운 뒤) 처리 시간이 짧고 유실되면 DNS 서버가 재질의를 하기 때문에 그걸로 받아오면 된다. 서버끼리 큰 파일을 주고받거나 암호화할 때만 TCP/TLS를 쓴다.

### 모범 답변

기본은 **UDP 53번 포트**다. 이유는 **보장하는 비용**이다.

| | TCP | UDP |
|---|---|---|
| 준비 | 3-way handshake 먼저 | 바로 보냄 |
| 종료 | 4-way handshake | 없음 |
| 결과 | 작은 질의 한 번에 연결·종료 비용이 더 크다 | 가볍고 빠르다 |

DNS 질의와 응답은 수십 바이트짜리 한 번의 주고받음이다. 유실되면 **질문한 쪽(리졸버)**이 몇 초 뒤 다시 묻거나 다른 DNS 서버에 묻는다. 질문이 작아서 다시 묻는 비용이 싸다.

TCP를 쓰는 경우도 있다.
- **응답이 UDP 한 패킷에 안 들어갈 만큼 클 때**(옛 한계 512바이트, DNSSEC 등)
- **DNS 서버끼리 데이터를 통째로 복사할 때(zone transfer)**
- **DNS를 암호화할 때(DoT, DoH)**

면접용 한 줄:
> "DNS는 질의·응답이 작고 한 번에 끝나서 handshake 비용이 아까우니 기본은 UDP 53번이고, 응답이 크거나 zone transfer, 암호화일 때는 TCP를 씁니다. 유실은 클라이언트가 재질의로 처리합니다."

### ✅ 맞게 알고 있던 부분

- (배운 뒤) **질의가 작고 빨리 끝난다**, **유실은 재질의로 처리한다**, **TCP는 큰 데이터 전송과 암호화에서 쓴다**를 모두 맞게 설명했다.
- 처음에 TCP라고 답한 이유(정확하게 전달해야 한다)는 좋은 사고방식이다. 거기에 **보장하는 비용**이라는 관점이 하나 더 필요했을 뿐이다.

### ❌ 잘못 알고 있던 부분

- **재질의는 DNS 서버가 하는 것이 아니다.** 질문한 쪽(클라이언트, 리졸버)이 응답이 없을 때 다시 묻는다. DNS 서버는 질문이 오면 답할 뿐이다.
- **빠진 것:** 응답이 너무 커서 UDP에 안 들어갈 때 TCP로 다시 묻는 경우.

## 실무 연결

- **DNS 캐시와 TTL:** 서버 IP를 바꿨는데도 사용자 일부가 옛 서버로 접속하는 일이 생긴다. DNS 응답에 TTL(캐시 유지 시간)이 있어서 그 시간 동안은 옛 IP를 쓰기 때문이다. 배포나 이전 때 TTL을 미리 줄여 둔다.
- **Keep-Alive와 커넥션 풀:** 화면 하나를 그리려고 요청이 여러 번 나가므로, 매번 3-way와 TLS handshake를 하면 느리다. 그래서 연결을 재사용한다(지난 TIME_WAIT 글과 이어진다).
- **응답 코드의 주체:** `200`, `404`, `500`은 모두 **서버가 보내는** 값이다. 장애 분석 때 "누가 이 코드를 만들었는가"를 구분해야 한다.
