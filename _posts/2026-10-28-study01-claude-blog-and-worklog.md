## 목적

공부하면서 배운 것을 블로그에 꾸준히 남기고 싶었다. 그런데 작업이 끝난 뒤에 기억을 더듬어 쓰면 빠지는 게 많다. "그때 왜 이렇게 바꿨더라?"가 제일 먼저 사라진다.

그래서 두 가지를 Claude에게 맡겼다.

- 작업하는 동안 **무엇을, 언제, 왜** 했는지 기록하기
- 그 기록을 재료로 **블로그 초안** 쓰기

단, 글은 반드시 내가 검수한 뒤에만 올라간다.

## 접근 방식

규칙 문서 두 개와 기록 파일 하나로 나눴다.

```
.claude/
├─ docs/
│   ├─ tracking.md     ← 무엇을 어떻게 기록할지
│   └─ blog.md         ← 언제, 어떤 형식으로, 어떤 절차로 쓸지
├─ worklog.md          ← 실제 기록 (시간 순)
└─ blog-drafts/        ← 검수 전 초안
```

흐름은 이렇다.

```
작업 중  ── 결정, 변경, 테스트, 문제 ──▶ worklog.md 에 한 줄씩
                                            │
기능이 production 에 들어감 ──▶ "글 쓸까요?" 제안
                                            │
                                            ▼
                                  blog-drafts/ 에 초안
                                            │
                                  공개 금지 정보 검색
                                            │
                                  내가 검수 → 수정 요청 반복
                                            │
                                  "올려" ──▶ 블로그 저장소에 커밋, push
```

## 처음 구상

처음에는 브랜치마다 블로그용 메모 파일을 따로 두려고 했다. `feat-xxx.md`에 그 브랜치 작업만 적는 식이다.

그런데 결정이 브랜치 단위로만 일어나지는 않는다. 블로그 형식을 바꾸거나, 규칙을 고치거나, 환경을 설정하는 일은 어느 브랜치에도 속하지 않는다. 그래서 **기록은 하나로 합치고**, 블로그는 그 기록에서 필요한 부분을 골라 쓰기로 했다.

## 구현

### 기록 형식

```
## 2026-10-28

- 13:20 [변경] 블로그 제목 형식
  - 바뀐 것: <이전> → <이후>
  - 이유: <내가 말한 이유 그대로>
- 13:58 [문제] MR 에 파이프라인이 생기지 않음
  - 원인: ...
  - 해결: ...
```

| 분류 | 언제 |
|---|---|
| `결정` | 규칙, 구조, 이름 등을 정했을 때 |
| `변경` | 이전 결정을 바꿨을 때 ("이전 → 이후" 필수) |
| `설계`, `구현` | 코드 설계를 컨펌하거나 파일에 반영했을 때 |
| `git`, `테스트` | 브랜치, 커밋, merge, 테스트 결과 |
| `문제` | 막힌 일과 원인, 해결 |
| `수정요청` | 내가 고쳐 달라고 한 것 |
| `보류` | 나중에 하기로 미룬 일 |

규칙은 두 가지를 강하게 걸었다.

- 지난 기록은 **고치거나 지우지 않는다.** 틀렸으면 새 줄로 "정정:"을 남긴다.
- 나중에 "언제 왜 그랬지?"라고 물으면, 기록에서 찾아 날짜와 이유를 함께 답한다. 기록에 없으면 추측하지 않는다.

### 블로그 형식

글은 공부한 주제별로 나눈다.

| 주제 | 제목 | 카테고리 |
|---|---|---|
| Kafka Consumer | `[STUDY_01][Kafka Consumer] <분류> - <내용>` | STUDY > KAFKA CONSUMER |
| Redis | `[STUDY_01][Redis] <분류> - <내용>` | STUDY > REDIS |
| Claude 활용 | `[STUDY_01][CLAUDE] <분류> - <내용>` | STUDY > CLAUDE |

분류는 `설정`, `기능`, `트러블슈팅`, `개념`, `테스트`, `성능` 중에서 고른다. 본문 순서도 정해 두었다.

```
목적 → 접근 방식
  → (문제 해결) 원인
  → (기능 개발) 처음 구상 → 구현 → 안 되면 다시 구상 → 구현
→ 겪은 문제 → 새로 배운 것
```

### 공개 전 점검

블로그는 누구나 본다. 그래서 `security.md`에 **공개하면 안 되는 정보**를 먼저 정의했다. 내부 주소, 계정과 토큰, 실제 데이터, 실제 설정값 같은 것들이다.

초안을 다 쓰면 Claude가 금지어 목록으로 초안을 검색하고, 결과를 초안과 함께 보여준다. 나는 내용과 점검 결과를 같이 보고 검수한다.

## 다시 구상

**제목 형식이 하루에 세 번 바뀌었다.** 처음엔 프로젝트 이름을 머리말로 썼다가, 주제별(`[KAFKA_CONSUMER]`, `[REDIS]`)로 바꿨고, 마지막에 분류를 붙인 `[STUDY_01][Kafka Consumer] 설정 - ...` 형식으로 정했다.

형식이 바뀔 때마다 `blog.md` 한 곳만 고쳤고, 바뀐 순서와 이유는 기록에 `변경`으로 남았다. 덕분에 "처음엔 왜 프로젝트 이름을 썼다가 바꿨지?"를 나중에 다시 확인할 수 있다.

**글의 범위도 다시 잡았다.** 처음 초안에는 "왜 이런 규칙을 만들었는지" 배경 설명이 길게 들어갔다. 검수하면서 보니 공부 기록에 필요 없는 이야기였다. 지금은 `blog.md` 맨 앞에 **"일반적인 내용만 쓴다"**를 두고, 배경보다 방법과 배운 점 위주로 쓴다.

## 겪은 문제

**1. 기록 시각을 추정해서 적었다.** Claude가 몇 줄을 실제 시각을 확인하지 않고 "대충 이쯤"으로 적었다. 나중에 보니 그 뒤 기록보다 시각이 늦었다. 지우지 않고 정정 줄을 남겼고, 규칙에 "시각은 **반드시 `date` 명령으로 확인**한다"를 추가했다.

**2. 새 기록이 보류 목록 밑에 붙었다.** 기록 파일 맨 아래에 보류 목록을 두었더니, 새 기록이 그 아래로 이어졌다. "새 기록은 보류 목록 위에" 한 줄을 규칙에 넣었다.

**3. 검수 때 지운 내용이 다시 들어갈 뻔했다.** 한 번 빼 달라고 한 성격의 문장은 다음 글에도 들어가면 안 된다. 그래서 수정 요청을 기록에만 남기지 않고, 반복될 만한 것은 `blog.md`나 `security.md` **규칙으로 올렸다.**

## 새로 배운 것

- 기록과 글은 분리하는 게 낫다. 기록은 빠짐없이, 글은 골라서.
- "지우지 말고 정정하라"는 규칙 하나로 기록을 믿을 수 있게 된다.
- 시각처럼 기계가 확인할 수 있는 값은 **확인하라고 명시**해야 한다.
- 검수에서 나온 지적은 그 글만 고치고 끝내지 말고, 규칙으로 올려야 다음에 반복되지 않는다.
