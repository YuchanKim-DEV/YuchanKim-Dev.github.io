세팅이 끝나고 "이제 뭘 만들지"를 정했다. 목표는 **백엔드라면 반드시 갖춰야 할 성질들을 직접 구현하고 겪어 보는 것**이다. 계획은 바뀔 수 있어서 리포의 [`docs/roadmap.md`](https://github.com/YuchanKim-DEV/SIDEPROJECT_LIMITED_DEALS/blob/main/docs/roadmap.md)에서 따로 관리한다.

## 왜 한정 특가인가

한정 수량 상품에 사람이 몰리면 백엔드의 어려운 문제가 한꺼번에 생긴다.

| 성질 | 한 줄 설명 | 한정 특가에서의 모습 |
|---|---|---|
| **동시성** | 여러 요청이 동시에 같은 데이터를 건드려도 결과가 맞아야 한다 | 재고 1개에 두 명이 동시에 주문하면 한 명만 성공해야 한다 |
| **멱등성** | 같은 요청을 여러 번 보내도 결과는 한 번 보낸 것과 같다 | 결제 버튼을 두 번 눌러도 주문은 한 건이어야 한다 |
| **데이터 유실 방지** | 장애가 나도 확정된 데이터와 이벤트가 사라지지 않는다 | 주문은 저장됐는데 알림 이벤트가 사라지면 안 된다 |
| **대용량** | 데이터가 많아져도 조회와 적재가 버틴다 | 주문이 수백만 건이 되어도 목록 조회가 느려지지 않아야 한다 |

## 새로 배운 것 1: 동시성 문제의 정체, Lost Update

```
사용자 A: 재고 조회(1) ─────────── 1 - 1 = 0 저장 ─ 주문 성공
사용자 B: 재고 조회(1) ─ 1 - 1 = 0 저장 ─────────── 주문 성공  ← 재고 1개에 주문 2건
```

둘 다 "재고가 1"이라고 읽고 각자 차감한다. 막는 방법은 여러 가지다.

| 방법 | 원리 | 한정 특가에서는 |
|---|---|---|
| 원자적 UPDATE | `UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0`, 영향받은 행이 0이면 품절 | 단순하고 빠르다 |
| 비관적 락 | `SELECT ... FOR UPDATE`로 잠그고 나머지는 대기 | 안전하지만 대기가 쌓인다 |
| 낙관적 락 | `@Version`으로 충돌을 감지하고 재시도 | 충돌이 많아서 재시도가 폭증한다 |
| Redis 원자 연산 | 메모리에서 `DECR`, Lua | 빠르지만 DB와 정합성을 맞춰야 한다 |

어떤 게 나은지는 직접 재현해서 숫자로 비교할 계획이다.

## 새로 배운 것 2: 멱등성은 DB 유니크 제약에 맡긴다

응답이 네트워크에서 사라지면 클라이언트는 같은 요청을 다시 보낸다. 해결은 요청마다 **멱등 키**(`Idempotency-Key`)를 붙이고, 서버가 이 키를 **유니크 제약이 있는 테이블**에 저장하는 것이다. 같은 키가 또 오면 새로 처리하지 않고 이전 결과를 돌려준다. 중복 확인을 코드의 `if`가 아니라 DB에 맡겨야 동시에 두 번 와도 한 건만 통과한다.

## 새로 배운 것 3: 이중 쓰기 문제와 Outbox

주문을 DB에 커밋한 직후 Kafka 발행 전에 서버가 죽으면, 주문은 있는데 이벤트는 없다. DB와 Kafka를 한 트랜잭션으로 묶을 수 없기 때문이다(**이중 쓰기 문제**). **Outbox 패턴**은 주문과 "보낼 이벤트"를 같은 DB 트랜잭션으로 저장하고, 별도 프로세스가 그걸 읽어 발행한다. 유실은 없지만 중복 발행은 생길 수 있어서, 받는 쪽도 멱등해야 한다.

## 새로 배운 것 4: 이것들은 비기능 요구사항의 일부일 뿐이다

"무엇을 하느냐"가 아니라 "얼마나 안정적이고 안전하게 하느냐"를 **비기능 요구사항**이라고 한다. 동시성과 멱등성 말고도 많다.

| 분류 | 성질 |
|---|---|
| 데이터 정합성 | 트랜잭션(ACID), 격리수준, 정합성 모델 |
| 장애 대응 | 타임아웃, 재시도(백오프), 서킷 브레이커 |
| 트래픽 보호 | Rate Limiting, 대기열, 백프레셔 |
| 성능, 확장 | 캐시, 인덱스, N+1, 커넥션 풀 |
| 보안 | 인증/인가(JWT), 입력 검증 |
| 관측 가능성 | 구조화 로그, 메트릭, 분산 추적 |
| 운영, 품질 | 동시성/부하 테스트, CI/CD, 무중단 스키마 변경 |

전부 하면 끝이 없어서 **면접에 자주 나오고 한정 특가에 직접 필요한 것**만 로드맵에 넣었다. 파티셔닝, 샤딩, 분산 추적 같은 건 데이터가 실제로 커진 뒤로 미뤘다.

## 로드맵

| 단계 | 주제 | 답해야 할 질문 |
|---|---|---|
| 0 | 기술 스택 세팅 | MySQL, Docker Compose, 스키마 관리 방식 |
| A | 재고 동시성 | 재고 1개에 100명이 동시에 주문하면 몇 건이 성공하나? |
| B | 주문 멱등성 | 결제 요청이 동시에 두 번 오면? |
| C | 대용량 조회와 적재 | 수백만 건에서 인덱스와 페이징으로 얼마나 빨라지나? |
| D | Redis | 캐시 정합성은? 캐시가 한꺼번에 만료되면? |
| E | 이벤트 신뢰성 | 저장은 됐는데 발행이 실패하면? 같은 이벤트가 두 번 오면? |
| F | 장애 대응 | 외부 결제 서버가 느려지면 우리 서버는? |
| G | 관측과 부하 테스트 | 초당 몇 건까지 버티나? 원인을 얼마나 빨리 찾나? |
| H | 보안 | 남의 주문을 볼 수 있나? |

원칙은 **문제를 먼저 겪고, 그다음에 기술을 도입하는 것**이다. 그래야 "왜 이 기술을 썼냐"에 답할 수 있다. 처음에는 F(장애 대응)와 H(보안)가 빠져 있었는데, 비기능 요구사항을 훑어보고 추가했다.

## DB는 MySQL

동시성은 실제 DB로 실험해야 한다. H2는 락과 격리수준 동작이 달라서 이 목적에 맞지 않는다. 국내 빅테크 면접에서 InnoDB의 격리수준, 갭 락, 인덱스 질문이 자주 나와서 **MySQL**로 정했다. 버전은 8.4 LTS로 고정했다(이 과정은 다음 Docker 글에서 다룬다).

## 진행 방식

- **구현은 내가 직접 입력한다.** AI(Claude)는 개념 설명과 완성된 명령, 파일 내용을 주고, 나는 그걸 따라 입력하고 실행한다. 실행 결과는 AI가 확인하고 리뷰한다. 처음에 AI가 이걸 "힌트를 주고 스스로 찾게 하는 방식"으로 이해해서 퀴즈처럼 진행됐는데, 바로잡았다.
- **큰 작업은 시작할 때 브랜치부터 만든다.** 하나의 목적을 가진 작업을 시작하면 최신 `main`에서 목적에 맞는 브랜치(`타입/설명/날짜`)를 먼저 만들고 그 위에서 작업한다. push 직전에 브랜치를 만들면 그동안 `main`에서 작업한 셈이고, 다른 목적의 변경이 섞이기 쉽다. 이 규칙도 컨벤션 문서에 추가했다.
- **머지된 브랜치는 AI가 정리하고, 위험한 작업 전에는 백업 브랜치를 만든다.** PR을 머지하면 로컬에 남은 작업 브랜치(`git fetch --prune` 후 원격이 사라진 것)를 `-d`로 지운다. 되돌리기 어려운 작업 전에는 `backup/설명/날짜-시각` 이름으로 로컬 백업 브랜치를 만들고, 최대 10개만 유지한다. 강제 삭제(`-D`)는 hook이 백업 브랜치에만 허용해서, 작업 브랜치를 실수로 날리는 일은 막힌다.
