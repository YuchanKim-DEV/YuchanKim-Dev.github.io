> 면접 질문 하나에서 시작해 꼬리질문까지 이어서 정리한다. 질문마다 **내 답변 → 모범 답변 → 맞게 알고 있던 부분 → 잘못 알고 있던 부분** 순서로 적는다.

## Q1. TCP와 UDP의 차이는? (시작 질문)

### 내 답변

TCP는 순서를 보장하고 UDP는 속도를 보장한다. UDP는 유실이 있어도 되지만 빨라야 하는 환경에서 쓰고, TCP는 속도가 느릴 수 있어도 데이터 유실이 없어야 하는 곳에서 쓴다.

### 모범 답변

TCP는 **연결 지향**이고 **신뢰성**을 보장한다. 3-way handshake로 연결을 맺고, 순서 번호와 ACK·재전송으로 데이터가 빠짐없이 순서대로 도착하게 한다. 흐름 제어와 혼잡 제어로 보내는 속도도 조절한다.

UDP는 **비연결형**이다. 연결 수립, 재전송, 순서 정렬을 하지 않는다. 대신 헤더가 작고 할 일이 적어서 지연이 낮다. 그래서 약간 유실돼도 괜찮고 실시간성이 중요한 곳(실시간 영상·음성, 게임, DNS 조회)에 쓴다.

| | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향 (3-way handshake) | 비연결형 |
| 신뢰성 | 유실 시 재전송, 순서 보장 | 보장 안 함 |
| 속도 조절 | 흐름 제어, 혼잡 제어 | 없음 |
| 데이터 단위 | 경계 없는 바이트 스트림 | 메시지(데이터그램) 단위 |
| 쓰임 | HTTP, 파일 전송, DB 연결 | 실시간 영상·음성, 게임, DNS |

### ✅ 맞게 알고 있던 부분

- TCP는 유실 없이 순서대로 전달하고, UDP는 유실을 허용하는 대신 빠르다.
- 어느 쪽을 고를지는 "유실이 괜찮은가, 속도가 중요한가"로 결정한다.

### ❌ 잘못 알고 있던 부분

- **"UDP는 속도를 보장한다"** → UDP는 **아무것도 보장하지 않는다.** 보장하는 게 없어서 할 일이 적고, 그래서 빠를 뿐이다. 면접에서 "속도 보장"이라고 하면 "어떻게 보장하나요?"라는 질문이 돌아온다.
- 처음 답에는 **TCP가 어떻게 보장하는지**(연결 수립, ACK·재전송, 순서 번호, 흐름·혼잡 제어)가 빠져 있었다. 면접의 꼬리질문은 거의 항상 "어떻게?"로 온다.

## Q2. 3-way handshake는 무엇이고, 왜 3번인가? (꼬리질문)

### 내 답변

엔드투엔드로 연결할 때 쓰는 인증 방식이다. A가 연결 신청을 보내면 B가 확인한 뒤 B도 A에게 연결 신청을 보내고, A도 확인하면 서로 인증이 완료되는 보안 방식이다.

### 모범 답변

TCP 연결을 맺는 절차다.

```
A → B : SYN        (연결하자, 내 시작 순서 번호는 x)
B → A : SYN + ACK  (좋아, x 받았다. 내 시작 순서 번호는 y)
A → B : ACK        (y 받았다)
```

목적은 두 가지다.
1. 양쪽 모두 **보내기와 받기가 된다**는 것을 확인한다.
2. 서로의 **시작 순서 번호**를 맞춘다.

**왜 3번인가:** 2번이면 B는 자기가 보낸 SYN+ACK가 A에게 도착했는지 모른다. 즉 "B → A 방향이 되는지"를 확인할 수 없다. 세 번째 ACK가 와야 양방향이 모두 확인된다.

### ✅ 맞게 알고 있던 부분

- 요청 → 확인 + 요청 → 확인으로 이어지는 **세 단계 흐름**은 정확하다.

### ❌ 잘못 알고 있던 부분

- **인증·보안 방식이 아니다.** handshake에는 상대가 누구인지 확인하는 기능이 없다. 보안은 TCP 위에서 **TLS**(HTTPS)가 따로 맡는다. 면접에서 "보안 방식"이라고 하면 TCP와 TLS를 구분하지 못한다고 보일 수 있다.

## Q3. 데이터를 못 받으면 어떻게 되는가? (꼬리질문)

### 내 답변

정한 시간 안에 한 번 더 보내도록 되어 있을 것이다.

### 모범 답변

받는 쪽은 받은 데이터에 대해 **ACK**(어디까지 받았는지)를 보낸다. 보내는 쪽은 정해진 시간(RTO) 안에 ACK가 오지 않으면 **다시 보낸다**(타임아웃 재전송). 같은 ACK가 여러 번 연속으로 오면 중간이 빠졌다고 보고 시간을 기다리지 않고 바로 다시 보내기도 한다(빠른 재전송).

### ✅ 맞게 알고 있던 부분

- **"정해진 시간 안에 응답이 없으면 다시 보낸다"**는 타임아웃 재전송의 핵심을 맞혔다.

### ❌ 잘못 알고 있던 부분

- 틀린 내용은 없다. 다만 **ACK**라는 용어와 "받는 쪽이 어디까지 받았는지 알려 준다"는 부분이 빠졌다. 다음 질문인 순서 번호와 함께 설명하면 답이 더 단단해진다.

## Q4. 순서 번호(sequence number)는 무슨 역할을 하는가? (꼬리질문)

### 내 답변

몰랐다. ("뭔 소리야"라고 되물음)

### 모범 답변

TCP는 보내는 데이터의 **바이트마다 번호**를 붙인다. 받는 쪽은 이 번호로 세 가지를 한다.
- 순서가 섞여 도착해도 **원래 순서대로 다시 맞춘다.**
- **빠진 번호**가 있으면 유실을 알아챈다. 그러면 ACK로 "여기까지 받았다"를 알려 재전송을 이끈다.
- **같은 번호**가 두 번 오면 중복으로 보고 버린다.

TCP의 "순서 보장"과 "유실 감지"는 모두 이 번호 덕분이다.

### ✅ 맞게 알고 있던 부분

- (해당 없음 — 처음 접한 개념)

### ❌ 잘못 알고 있던 부분

- 순서 번호를 몰랐다. 그래서 Q1에서 "TCP는 순서를 보장한다"고 답했지만 **어떻게** 보장하는지는 설명할 수 없었다. "순서 보장 = 순서 번호", "유실 방지 = ACK + 재전송"으로 짝지어 외운다.

## Q5. 흐름 제어와 혼잡 제어는 각각 무엇을 보호하는가? (꼬리질문)

### 내 답변

결국 데이터 유실을 막아 데이터를 보호하기 위한 것이다. 흐름을 제어해야 데이터가 중복인지 유실인지 알 수 있고, 혼잡 제어를 해야 마찬가지로 중복·유실을 판단할 수 있다.

### 모범 답변

둘 다 "보내는 속도를 줄이는" 기능이지만 **보호하는 대상이 다르다.**

| | 흐름 제어 | 혼잡 제어 |
|---|---|---|
| 보호 대상 | **받는 쪽**(수신 버퍼) | **네트워크**(중간 라우터들) |
| 문제 상황 | 받는 쪽이 처리하는 속도보다 빨리 보내서 버퍼가 넘침 | 네트워크 전체에 데이터가 몰려 라우터에서 패킷이 버려짐 |
| 기준 | 받는 쪽이 알려 주는 남은 공간(수신 윈도우) | 보내는 쪽이 유실·지연을 보고 추정한 혼잡 정도(혼잡 윈도우) |
| 한 줄 | "받는 사람이 감당할 만큼만" | "도로가 막히지 않을 만큼만" |

### ✅ 맞게 알고 있던 부분

- **결국 유실을 줄이기 위한 장치**라는 큰 방향은 맞다. 받는 쪽 버퍼가 넘치거나 라우터가 패킷을 버리면 유실이 생기는데, 두 기능 모두 그걸 막으려고 속도를 조절한다.

### ❌ 잘못 알고 있던 부분

- **중복·유실을 "판단"하는 건 흐름·혼잡 제어가 아니다.** 그건 Q4의 **순서 번호와 ACK**가 한다. 흐름·혼잡 제어는 판단이 아니라 **보내는 양을 조절**하는 기능이다.
- **둘의 차이(보호 대상)**를 구분하지 못했다. 면접에서 이 질문의 핵심은 "흐름 제어 = 받는 쪽, 혼잡 제어 = 네트워크"다.

## 실무 연결

TCP는 **경계 없는 바이트 스트림**이라 "메시지 하나가 어디서 끝나는지"를 TCP가 알려 주지 않는다. 그래서 TCP 위에서 직접 서버를 만들 때는 메시지 경계를 정해야 한다. 예를 들어 앞에 길이를 붙이거나 구분자를 쓴다(Netty의 `LengthFieldBasedFrameDecoder` 등). UDP는 메시지 단위로 오가기 때문에 이 문제가 없다.

- HTTP/3(QUIC)는 왜 UDP 위에서 동작하는지
