## 3. 온라인 오픈런 흐름

```
① 오픈 시각에 접속 → ② 사람이 많으면 번호표 받고 대기 ("내 순번 3,421번")
→ ③ 순서가 오면 N분짜리 입장권 → ④ 구매(재고 차감) → ⑤ 주문 확정 이벤트 발행
```

화면은 꾸미지 않는다. **테스트 시작 버튼, 순번 화면, 지표·로그 대시보드**만 만든다.

## 4. 구상도

```
                 [k6] 1만~10만 명 동시 요청
                          │
                 ┌────────▼────────┐
                 │     gateway     │  입구. Rate Limit(Redis)
                 └───┬─────────┬───┘
       ┌─────────────▼──┐   ┌──▼─────────────────────┐
       │ queue-service   │   │ order-service           │
       │ 번호표, 입장권    │   │ 재고 차감 + 주문 + outbox │
       └──────┬──────────┘   └──────┬─────────────────┘
              ▼                     ▼           │ 릴레이
           [Redis]              [MySQL]         ▼
                                           [Kafka] 상품 id 기준 순서
                                                ▼
                                  [컨슈머] Inbox로 중복 제거

  관측: Prometheus + Loki → Grafana / 실행: docker compose → Kubernetes
```

서버는 처음에 3개(gateway, queue-service, order-service)로 시작했다. 리포는 하나에 Gradle 모듈만 나눴고, 각 모듈이 따로 실행되고 따로 배포된다.

## 5. 새로 배운 것

### Kafka와 Redis는 경쟁이 아니라 보완 관계다

| | Kafka | Redis |
|---|---|---|
| 본질 | 디스크에 저장하는 이벤트 로그 | 메모리 기반 저장소 |
| 강점 | 유실 없음, 재처리, 파티션 안 순서 보장 | 매우 빠름, 원자 연산, 만료(TTL) |
| 이 프로젝트에서 | 확정된 주문을 잃지 않고 전달 | 몰려드는 요청을 빠르게 거르고 줄 세우기 |

### Redis Pub/Sub는 이벤트 전달에 쓰면 안 된다
Pub/Sub는 메시지를 저장하지 않아서, 받는 쪽이 잠깐 꺼져 있으면 그 사이 메시지가 사라진다. 유실 방지가 목표라 이벤트는 Kafka로 보내고, Redis는 대기열, 카운터, Rate Limit에만 쓴다.

### 보내는 쪽은 Outbox, 받는 쪽은 Inbox
Outbox는 주문과 "보낼 이벤트"를 **같은 DB 트랜잭션**으로 저장하는 전용 테이블이다. 릴레이가 이걸 읽어 Kafka로 보낸다. 발행 후 "보냄" 표시 전에 죽으면 같은 이벤트를 또 보낼 수 있어서, 받는 쪽은 처리한 이벤트 id를 저장하는 **Inbox**로 중복을 걸러낸다.

### 브라우저로는 1만 번을 동시에 누를 수 없다
브라우저는 한 서버에 동시 연결을 몇 개밖에 못 연다. 화면에는 "시작" 버튼만 두고, 실제 요청은 **k6**가 보낸다. "완전히 같은 순간"은 없고 실제로는 몇십~몇백 ms 안에 몰리는 것이라, k6로 1만 명이 한 번씩 누르는 상황을 만든다. 노트북 한 대로는 한계가 있어서 1천 → 5천 → 1만으로 올리며 어디서 무너지는지 본다.

### MSA의 이점과 비용
| 이점 | 비용 |
|---|---|
| 대기열 서버만 따로 늘리기 | 서비스마다 DB가 달라 하나의 트랜잭션이 안 됨 (Saga, Outbox 필요) |
| 대기열이 죽어도 주문은 계속됨 | 서비스 간 네트워크 장애, 추적의 어려움 |

"MSA를 왜 썼냐"에 "요즘 많이 써서"라고 답하면 감점이다. 이 프로젝트의 답은 **"대기열과 주문의 트래픽이 100배 차이 나서, 대기열만 따로 늘리려고"**다. 그리고 이걸 7단계에서 Kubernetes로 대기열 서버만 늘려 숫자로 보여줄 계획이다.

## 6. 계획표

| 단계 | 할 일 | 확인할 질문 |
|---|---|---|
| 0. 기반 | 서버 3개 분리, MySQL·Redis | 입구가 각 서버로 안내하는가? (완료) |
| 1. 재고 동시성 | 초과 판매 재현 → 락 3가지 비교 | 재고 1개에 1만 명이 사면 몇 건이 팔리나? |
| 2. 주문 멱등성 | 멱등 키 + 유니크 제약 | 결제 버튼을 동시에 두 번 누르면? |
| 3. 대기열 | 번호표, 입장 제어, 입장권, Rate Limit | 10만 명이 몰려도 서버가 안 죽나? |
| 4. 이벤트 신뢰성 | Kafka, Outbox, Inbox, DLQ | 서버가 죽어도 이벤트가 사라지지 않나? |
| 5. 장애 대응 | 타임아웃, 재시도, 서킷 브레이커 | 한 서버가 죽으면 나머지는 버티나? |
| 6. 관측과 부하 | Grafana, 병목 찾기, 가상 스레드 | 초당 몇 건까지 버티나? |
| 7. 확장과 배포 | Docker 이미지, Kubernetes | 대기열 서버를 늘리면 처리량이 얼마나 오르나? |
| 8. 결제·정산 | 원장, 대사, Saga | 주문·결제·재고 숫자가 항상 맞나? (보류) |
| 9. 보안 | JWT, 입력 검증 | 남의 주문을 볼 수 있나? (보류) |

단계마다 **측정 숫자, 장애 보고서(Post-mortem), 블로그 글**을 남긴다. 다음 글은 1단계, 재고 동시성이다.
