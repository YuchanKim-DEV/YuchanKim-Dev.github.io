## Q1. HTTP와 HTTPS의 차이는 무엇이고, HTTPS는 어떻게 안전하게 통신하나? (시작 질문)

### 내 답변

(처음) 보안 차이다. S는 Secure를 뜻한다. TCP 소켓으로 3-way handshake를 진행하고, 데이터를 옮길 때는 패킷으로 옮긴다.

(배운 뒤) HTTP와 HTTPS 모두 TCP 3-way handshake를 하는 것은 같다. HTTPS에는 TLS 과정이 들어가 있다. TLS에서 암호화를 하고, 무결성 검사를 하고, 인증서로 신원을 확인한다.

### 모범 답변

**HTTPS = HTTP + TLS.** HTTP는 데이터를 평문으로 보낸다. HTTPS는 TCP와 HTTP 사이에 TLS 층을 끼워서 암호화한다. 기본 포트는 HTTP 80, HTTPS 443이다.

```
HTTP        HTTPS
            HTTP
            TLS    ← 암호화·무결성·인증
TCP         TCP    ← 3-way handshake는 둘 다 한다
```

평문 HTTP에는 세 가지 위험이 있다. TLS는 이 셋을 하나씩 막는다.

| 위험 | TLS의 해결책 |
|---|---|
| **도청**: 내용을 엿본다 | 암호화 |
| **변조**: 내용을 바꿔치기한다 | 무결성 검사(MAC) |
| **위장**: 가짜 서버가 진짜인 척한다 | 인증서(CA 서명) |

**TLS handshake 흐름** (TCP 3-way handshake가 끝난 뒤)

1. **Client Hello**: 클라이언트가 쓸 수 있는 암호 방식 목록과 랜덤값을 보낸다.
2. **Server Hello + 인증서**: 서버가 암호 방식을 고르고, 공개키가 담긴 인증서를 보낸다.
3. **인증서 검증**: 브라우저가 미리 가지고 있는 CA(인증기관) 목록으로 "믿을 만한 기관이 서명한 인증서인가?"를 확인한다.
4. **키 교환**: 양쪽이 같은 **대칭키(세션 키)**를 만든다.
5. 이후 데이터는 전부 그 대칭키로 암호화해서 주고받는다.

### ✅ 맞게 알고 있던 부분

- 핵심 차이가 **보안**이고 S가 **Secure**라는 것.
- (배운 뒤) TLS가 하는 일 세 가지(암호화·무결성·인증)를 정확히 말했다.

### ❌ 잘못 알고 있던 부분

- **3-way handshake를 HTTPS의 특징처럼 말했다.** 3-way handshake는 TCP가 연결할 때 하는 절차라 HTTP와 HTTPS 둘 다 한다. 차이점이 될 수 없다. ([TCP vs UDP 글]({% post_url 2026-10-29-cs-tcp-vs-udp %})에서도 handshake를 보안 방식으로 오해했었다. 같은 구멍이다.)
- "패킷으로 옮긴다"도 둘 다 같다.
- 처음 답에는 **HTTPS가 실제로 무엇을 하는지(TLS)**가 빠져 있었다.

## Q2. HTTPS는 왜 대칭키와 비대칭키를 둘 다 쓰는가? (꼬리질문)

### 내 답변

대칭키는 둘이 같은 키를 쓰기 때문에 유출 문제가 있다. 비대칭키도 같이 쓰면 개인키를 사용하여 보안에 더 신경 쓸 수 있다. 그리고 속도 차이도 있다. 비대칭키로 소통하는 주체를 인증하고, 그 이후로 대칭키로 데이터를 주고받는다(빠름).

### 모범 답변

| | 대칭키 | 비대칭키(공개키) |
|---|---|---|
| 방식 | 잠그는 키 = 여는 키 | 공개키로 잠그면 개인키로만 열림 |
| 속도 | 빠르다 | 느리다(수백~수천 배) |
| 약점 | **처음에 키를 상대에게 안전하게 넘길 방법이 없다**(키 배송 문제) | 대량 데이터 암호화에 쓰기엔 너무 느리다 |

그래서 둘을 섞는다.

- **처음 한 번**: 비대칭키 방식(또는 키 교환 알고리즘)으로 **대칭키를 안전하게 공유**한다.
- **그 뒤 모든 데이터**: 빠른 대칭키로 암호화한다.

참고로 요즘 TLS 1.3은 서버 공개키로 대칭키를 직접 잠그지 않는다. **ECDHE 키 교환**으로 양쪽이 각자 계산해서 같은 대칭키를 만든다. 그래도 "느린 방식으로 키를 정하고, 빠른 대칭키로 데이터를 보낸다"는 큰 그림은 같다.

### ✅ 맞게 알고 있던 부분

- **처음엔 비대칭키, 이후 데이터는 대칭키**라는 순서.
- 그 이유가 **속도**라는 것.

### ❌ 잘못 알고 있던 부분

- 대칭키의 문제를 "같은 키라서 유출된다"고 했다. 더 정확히는 **"그 같은 키를 처음에 상대에게 어떻게 안전하게 넘기나"**가 문제다(키 배송 문제). 비대칭키는 바로 이 문제를 풀려고 쓴다.
- "비대칭키로 주체를 인증한다"고 했다. 상대가 진짜인지 확인하는 일은 **인증서(CA 서명)**가 한다. TLS에서 비대칭키 단계의 주된 역할은 **대칭키를 안전하게 공유하는 것**이다.

## Q3. 인증서가 없으면 암호화만으로는 무엇을 못 막는가? (꼬리질문)

### 내 답변

인증서가 없으면, 암호화를 한다고 해도 신원이 확인되지 않은 곳에 데이터를 전달할 수 있기 때문에 보안이 뚫려 버린다.

### 모범 답변

**중간자 공격(MITM, Man-In-The-Middle)**을 못 막는다.

```
클라이언트  ⇄  공격자  ⇄  진짜 서버
```

공격자가 중간에서 서버인 척 **자기 공개키**를 클라이언트에게 준다. 클라이언트는 그 키로 열심히 암호화하지만, 그 키의 주인은 공격자다. 공격자는 내용을 다 풀어 본 뒤 진짜 서버에 다시 암호화해서 넘긴다. 양쪽 다 정상적으로 통신한다고 믿는다.

인증서는 "이 공개키는 정말 이 도메인의 것"이라고 CA가 서명한 문서다. 공격자는 CA의 서명을 위조할 수 없다. 그래서 브라우저가 가짜 키를 걸러낸다.

### ✅ 맞게 알고 있던 부분

- **"신원이 확인되지 않은 곳에 데이터를 보낼 수 있다"**는 핵심을 정확히 짚었다. 암호화와 인증이 서로 다른 문제라는 걸 이해했다.

### ❌ 잘못 알고 있던 부분

- 틀린 내용은 없다. **중간자 공격(MITM)**이라는 용어를 더하면 면접 답변으로 완성된다.

## 실무 연결

- Spring Boot 서버 앞단의 로드밸런서나 Nginx가 443으로 TLS를 풀고, 내부에는 80(HTTP)으로 넘기는 구성을 **TLS 종료(TLS termination)**라고 한다. 서버 코드에서 `request.isSecure()`가 false로 나오는 이유가 보통 이것이다.
- HTTPS도 매번 TLS handshake를 하면 느리다. 그래서 **Keep-Alive**(지난 글의 커넥션 재사용)와 **세션 재개**(이전 키 재사용)로 handshake 횟수를 줄인다.
