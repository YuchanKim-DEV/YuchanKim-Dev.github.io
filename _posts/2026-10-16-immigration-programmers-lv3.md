## 문제 설명

`n`명이 입국심사를 기다리고, 심사관마다 한 명을 심사하는 시간 `times[i]`가 다르다. 한 심사대는 한 번에 한 명만 심사하고, 더 빨리 끝나는 심사대가 있으면 기다렸다가 그곳으로 갈 수도 있다. 모든 사람이 심사를 받는 데 걸리는 **최소 시간**을 구한다. 사람은 최대 10억 명, 심사 시간도 최대 10억 분이다.

```
n = 6, times = [7, 10] → 28
```

## 시행착오

전날 Lv3라는 숫자에 부담을 느껴 Easy(LC1351)와 LC35 백지 재작성으로 감각을 먼저 되찾은 뒤에 풀었다.

### 0차: 공배수로 접근하려 함

"1, 1, 1의 최소공배수는?"을 먼저 물었다. 이 문제에는 공배수가 필요 없고, **나눗셈의 몫** 하나면 된다.

> T분 동안 한 심사관이 심사할 수 있는 사람 수 = `T / 심사시간` (몫)

`times = [7, 10]`에서 28분이면 `28 / 7 = 4`명, `28 / 10 = 2`명, 합계 6명이라 6명을 다 심사할 수 있다.

### 1차: "감이 안 온다" → 시간을 하나씩 넣어 본 표

| T(분) | 7분 심사관 | 10분 심사관 | 합계 | 6명 가능? |
|---|---|---|---|---|
| 26 | 3 | 2 | 5 | ✗ |
| 27 | 3 | 2 | 5 | ✗ |
| **28** | **4** | **2** | **6** | **✓** |
| 29 | 4 | 2 | 6 | ✓ |

"가능?" 칸은 **✗ ✗ ✓ ✓**처럼 한 번 ✓가 되면 계속 ✓다. 그래서 답은 **처음으로 가능해지는 시간**이고, 이는 방금 푼 LC35의 "target 이상인 첫 위치"와 같은 모양이다.

### 2차: 판단을 `mid % n`으로 씀

```java
if ((mid % n) == 0) { right = mid; } else { left = mid + 1; }
```

"`mid`가 `n`의 배수인가?"를 물었다. 문제가 묻는 건 "**`mid`분이면 n명을 다 심사할 수 있나?**"다. 28분이면 `28 % 6 = 4`라서 "불가능"으로 봤지만 실제로는 6명 가능이다. 판단은 **모든 심사관의 `mid / times[i]`를 더해 `n` 이상인지**로 바꿨다.

### 3차: 범위를 0에서 시작하는 `min`

```java
long right = 0;
right = Math.min(times[i] * n, right);   // 0과 min → 계속 0
```

"가장 빠른 심사관 혼자서 n명"을 상한으로 잡으려는 생각은 맞았지만, 0에서 시작하면 `min`은 영원히 0이라 반복이 한 번도 돌지 않았다. 시작값을 `Long.MAX_VALUE`로, 곱하기는 `(long) times[i] * n`으로 바꿨다.

### 4차: 로컬은 통과, 프로그래머스는 실패 — `int sum`

```java
int sum = 0;
sum += mid / times[i];                   // += 는 long을 int로 "조용히" 잘라 넣는다
```

로컬 테스트 8개는 다 맞았는데 제출하면 실패였다. 확인해 보니 `n = 10억, times = [1,1,1,1,1]`에서 정답 2억 대신 10억이 나왔다. `mid = 5억`이면 합이 25억이라 `int`(약 21억)를 넘어 음수로 깨지고, "불가능"으로 판단했기 때문이다. **`+=`는 결과를 자동으로 `int`로 잘라 넣어서 컴파일 에러도 나지 않는다.** `long sum`으로 바꿔 통과했다.

## 최종 코드

```java
public long solution(int n, int[] times) {
    long left = 0;
    long right = Long.MAX_VALUE;
    for (int i = 0; i < times.length; i++) {
        right = Math.min((long) times[i] * n, right);   // 가장 빠른 심사관 혼자 n명
    }
    while (left < right) {
        long mid = left + (right - left) / 2;
        long sum = 0;                                   // int면 큰 입력에서 넘침
        for (int i = 0; i < times.length; i++) {
            sum += mid / times[i];                      // mid분 동안 처리한 사람 수
        }

        if (sum >= n) {
            right = mid;                                // 가능 → 더 짧게
        } else {
            left = mid + 1;                             // 불가능 → 더 길게
        }
    }
    return left;                                        // 처음으로 가능해지는 시간
}
```

로컬 8개 통과, 랜덤 20,000건에서 정답과 일치, 심사관 10만 명 입력도 1ms였다.

## 오늘 배운 내용

**"최솟값을 구하라 + 입력이 너무 커서 시뮬레이션이 불가능"하면 답을 이진 탐색한다(파라메트릭 서치).** 답 후보(시간)를 하나 정해서 "이걸로 되나?"만 판단하면, ✗✗✓✓처럼 갈라지는 경계를 이진 탐색으로 찾을 수 있다. 875 바나나(속도 탐색)와 같은 틀이고, 탐색하는 값만 "시간"으로 바뀌었다.

**계산 결과가 커질 수 있는 변수는 처음부터 `long`이다.** 특히 `+=`, `*=` 같은 복합 대입은 타입을 자동으로 잘라 넣어서 넘침이 조용히 일어난다.

## 오답노트

- **틀렸던 지점 1**: 공배수로 접근. **왜**: "여러 심사관이 동시에 일한다"를 주기 문제로 착각했다. **다음에**: "T분이면 몇 개?"는 몫(`T / 시간`)으로 센다.
- **틀렸던 지점 2**: 판단을 `mid % n == 0`. **왜**: "가능한가?"를 숫자 성질로 바꿔 버렸다. **다음에**: 판단 함수는 문제 문장("n명을 다 심사할 수 있나")을 그대로 계산한다.
- **틀렸던 지점 3**: `min`의 시작값 0. **왜**: 최솟값을 구할 때 시작값은 아주 큰 수여야 한다는 걸 놓쳤다. **다음에**: `min`은 `MAX_VALUE`, `max`는 `MIN_VALUE`(또는 첫 원소)에서 시작한다.
- **틀렸던 지점 4**: `int sum`. **왜**: 로컬 테스트에 큰 합계가 나오는 경우가 없어서 통과했다. **다음에**: 제약이 10억 단위면 합계·곱셈 변수는 무조건 `long`, 곱하기 전에 `(long)` 캐스팅.
- **좋았던 점**: "처음으로 가능해지는 시간"을 LC35와 연결하자 구조(`right = mid`, `left = mid + 1`, `return left`)는 바로 잡았다.

## 꿀팁

Java의 복합 대입(`+=`, `-=`, `*=`)은 `a = (a의 타입)(a + b)`와 같다. 그래서 `int sum; sum += longValue;`는 에러 없이 컴파일되고 **넘친 값이 잘린 채로** 들어간다. 큰 수를 다루는 문제에서는 합계 변수의 타입부터 확인한다.

## AI라면 어떻게 풀었을까

같은 파라메트릭 서치를 **`left <= right` + `answer` 변수** 틀로 쓴다. 가능한 시간을 찾을 때마다 `answer`에 기록하고 더 짧은 시간을 찾으러 `right = mid - 1`로 간다. 또 판단 반복 안에서 합계가 `n` 이상이 되는 순간 `break`해서 나머지 심사관을 볼 필요를 없앤다.

```java
public long solutionAlt(int n, int[] times) {
    long left = 1;
    long right = (long) Arrays.stream(times).max().getAsInt() * n;   // 가장 느린 심사관 혼자 n명
    long answer = right;
    while (left <= right) {
        long mid = left + (right - left) / 2;
        long done = 0;
        for (int t : times) {
            done += mid / t;
            if (done >= n) {
                break;                        // 이미 n명 처리 가능
            }
        }
        if (done >= n) {
            answer = mid;                     // 가능 → 기록하고 더 줄여 본다
            right = mid - 1;
        } else {
            left = mid + 1;                   // 불가능 → 시간을 늘린다
        }
    }
    return answer;
}
```

트레이드오프: `answer` 변수 덕분에 "반복이 끝났을 때 `left`가 답인가 `right`가 답인가"를 고민하지 않아도 된다. 상한은 넉넉하게 "가장 느린 심사관 혼자"로 잡아서 계산이 단순하다. 대신 `answer` 변수를 하나 더 관리해야 하고, 상한이 커서 반복이 한두 번 더 돌 수 있다(둘 다 `O(심사관 수 × log(시간))`). 랜덤 20,000건에서 본인 풀이와 출력이 일치했다.
